## High

### Path traversal via unsanitized `providedSlug`
- **File**: `src/pages/api/publish-note.ts:70`
- **Issue**: `providedSlug` is taken directly from the request body and interpolated into `filePath` without sanitization: `const filePath = \`src/content/notes/${slug}.md\``. A caller with the API key can pass `slug = "../../pages/api/evil"` to write a `.md` file to `src/pages/api/evil.md` (normalized by the GitHub API). While the `.md` extension limits code-execution risk, this can overwrite existing source files, create rogue pages that Astro serves, or trigger build failures. `providedSlug` bypasses the `slugify()` call that would strip `/` and `..` sequences.
- **Fix**: Validate `providedSlug` with the same character-set restriction used for generated slugs — e.g., `if (!/^[a-z0-9-]{1,100}$/.test(providedSlug)) return 400`. This keeps the slug safe while preserving caller control.

### YAML frontmatter encoding bug — strings with both `"` and `'`
- **File**: `src/pages/api/publish-note.ts:18-31`
- **Issue**: `buildFrontmatter` wraps strings containing `"` in single quotes (`'${v}'`) without escaping internal single quotes. A title like `Brady's "guide" to X` produces `title: 'Brady's "guide" to X'` — invalid YAML because the single quote inside is unescaped (YAML single-quoted scalars require `''` to represent a literal `'`). Astro's content collection parser will reject the file, and the next Vercel deploy will fail to build. The same issue applies to array items in `tags`: items containing `"` are inserted with bare `"${s}"` formatting inside inline YAML arrays, producing `["a "b" c"]` which is invalid.
- **Fix**: Use a proper YAML escaping helper. The simplest safe approach is to always use double-quoted scalars and escape any `"` inside as `\\"`:
  ```ts
  function yamlStr(v: string): string {
    return `"${v.replace(/\\/g, "\\\\").replace(/"/g, '\\"')}"`;
  }
  ```
  For tags, apply the same escaping per element.

## Medium

### Rate limiter fails open during Redis outage
- **File**: `src/pages/api/trips/auth.ts:15-27`
- **Issue**: When Redis is unavailable, `checkRateLimit` logs and returns `true` (allow). This is a documented, intentional design decision — the comment explains that failing closed would lock out all users. The tradeoff is acceptable, but it means that any Redis outage is also a window during which unlimited brute-force attempts against `TRIP_PIN` are possible. If `expire` succeeds but `incr` fails on a subsequent request, the counter also resets unpredictably. A secondary defense (e.g., IP-based rate limiting at the Vercel edge/WAF level) would eliminate this window without changing the application-level logic.
- **Fix**: Add Vercel Edge Config or WAF rate limiting as a secondary layer so application-level Redis failure doesn't fully expose the auth endpoint.

### Non-constant-time PIN comparison
- **File**: `src/pages/api/trips/auth.ts:68`
- **Issue**: `pin !== PIN` is a short-circuit string comparison. Theoretically it leaks timing information about how many leading characters match. In practice, the network round-trip time overwhelms any such signal, and the rate limiter (5 req/min) prevents statistical accumulation. Risk is negligible for this use case.
- **Fix**: If a stricter posture is ever needed, replace with `crypto.timingSafeEqual(Buffer.from(pin), Buffer.from(PIN))` (Node) or an equivalent constant-time compare.
