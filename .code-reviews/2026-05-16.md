## High

### Vote toggle is not atomic — concurrent taps can corrupt state
- **File**: `src/pages/api/trips/vote.ts:72-80`
- **Issue**: The `toggle` path does a Redis `hget` followed by either `hset` or `hdel`. If two requests for the same `optionId:voter` pair arrive simultaneously (e.g., a double-tap on mobile or two browsers open at once), both can read the current value as absent, and both will then `hset "1"` — or both can read `"1"` and both `hdel`, leaving the vote in the wrong final state.
- **Fix**: Replace the read-modify-write pair with a Lua script or a Redis transaction (Upstash supports `EVAL`). A minimal atomic toggle in Lua:
  ```lua
  local val = redis.call('HGET', KEYS[1], ARGV[1])
  if val == '1' then
    redis.call('HDEL', KEYS[1], ARGV[1])
    return 0
  else
    redis.call('HSET', KEYS[1], ARGV[1], '1')
    return 1
  end
  ```
  Call with `redis.eval(script, keys=[VOTE_KEY], arguments=[field])` and remove the separate `hget`/`hset`/`hdel` calls.

## Medium

### `verifyToken` doesn't guard against empty secret — API routes can be bypassed on misconfigured deployments
- **File**: `src/middleware.ts:14-29`
- **Issue**: `SECRET` is resolved once as `import.meta.env.TRIP_SECRET || ""`. The exported `verifyToken` function never checks whether `SECRET` is empty before signing. The middleware's guard (`if (!SECRET) return 500`) protects browser navigation through `/trips/*`, but the API routes (`/api/trips/vote`, `/api/trips/votes`) call `verifyToken` directly. If `TRIP_SECRET` is unset in a Vercel environment, those routes accept any token computed with an empty HMAC key — an attacker who knows the token format (`${issuedAt}:${expiresAt}.${sig}`) can compute `HMAC-SHA256("", payload)` and forge a valid cookie.
- **Fix**: Add an explicit guard at the top of `verifyToken`:
  ```ts
  export async function verifyToken(token: string): Promise<boolean> {
    if (!SECRET) return false;
    // rest of function unchanged
  ```
  This makes the function fail-closed regardless of call site.

### Real PII hardcoded in source — flight numbers, seat assignments, hotel phone, family names
- **File**: `src/pages/trips/nyc-2026.astro:30-67`, `src/lib/redis.ts:37`
- **Issue**: Five family members' names, four Delta flight numbers with specific seat assignments, travel dates, hotel name, and hotel phone number are committed to source. If this repo is public on GitHub, that data is world-readable regardless of the auth gate on the rendered page. Flight seat data is particularly sensitive (enables social engineering, seat-stealing scams).
- **Fix**: Move trip-specific itinerary data out of source code. Options in increasing rigor: (a) keep the repo private, (b) load flight/itinerary data from a JSON file excluded in `.gitignore`, or (c) store structured trip data in Redis and fetch it at request time. The `VOTERS` list in `redis.ts` (first names only) is low risk, but the seat assignments in `nyc-2026.astro` should not be in a public commit history.

## Low

### `VOTE_KEY` hardcoded to a specific trip slug
- **File**: `src/lib/redis.ts:36`
- **Issue**: `export const VOTE_KEY = "trip:nyc-2026:votes"` couples the Redis key to this trip. When the next trip is planned, the constant will either need a code change or will silently reuse stale data from a different trip if someone forgets to update it.
- **Fix**: Derive the key from a config value or env var (`TRIP_SLUG`), or pass the trip ID explicitly to functions that need it. This also makes it easier to test multiple concurrent trip plans.

### Auth endpoint responses missing `cache-control: no-store`
- **File**: `src/pages/api/trips/auth.ts:34-51`
- **Issue**: The `POST /api/trips/auth` handler returns `200`, `400`, `429`, and `500` responses without a `Cache-Control: no-store` header. A CDN, shared proxy, or aggressive browser cache could cache a `429 Too many attempts` response and block a legitimate retry that would otherwise succeed. The `GET /api/trips/votes` route correctly sets `no-store`; auth should match.
- **Fix**: Add `"cache-control": "no-cache, no-store"` to all response `headers` objects in `auth.ts`, mirroring what `votes.ts:45` already does.
