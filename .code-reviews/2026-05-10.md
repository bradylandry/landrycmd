## Critical

### Auth middleware explicitly skips all `/trips/api/*` routes
- **File**: `src/middleware.ts:43`
- **Issue**: The middleware contains `if (pathname.startsWith("/trips/api/")) return next();` which unconditionally bypasses the auth check for every API endpoint under `/trips/`. The vote endpoint (`/api/trips/vote`) and the votes read endpoint (`/api/trips/votes`) are both reachable without a valid cookie. Any anonymous user can cast or overwrite votes for any named family member.
- **Fix**: Remove the `/trips/api/` bypass entirely — the API routes live at `/api/trips/*` (not `/trips/api/*`), so the bypass is also logically dead code. The actual routes already export `prerender = false` and are correctly under `/api/`, outside the `/trips/` prefix, so the middleware already does not gate them. The dead bypass line is harmless to delete but gives a false sense that API auth was considered and decided against; clarify with a comment or remove. More importantly: add an explicit auth check inside `vote.ts` and `votes.ts` that validates the session cookie using the same `verifyToken` logic, so the API layer enforces authentication independently of the middleware route-matching.

### Vote endpoint accepts arbitrary voter identity without authentication
- **File**: `src/pages/api/trips/vote.ts:40`
- **Issue**: The `voter` field is taken directly from the request body and only validated against the hardcoded `VOTERS` list (`isVoter()`). There is no check that the authenticated session corresponds to the claimed voter. Any caller — authenticated or not — can POST `{ optionId: "...", voter: "stacy", action: "set" }` and record a vote on behalf of another family member. Combined with the middleware bypass above, the voting data is completely untrustworthy.
- **Fix**: Encode the voter identity into the HMAC token at login time (e.g., prompt for name selection on the login page before issuing the token, then embed `voter:<name>` in the token payload). Validate on the server that the session token's embedded voter matches the posted `voter` field. Alternatively, maintain a server-side session map. At minimum, ensure that the route requires a valid cookie before processing any mutation.

## High

### In-memory rate limiter resets on every cold start
- **File**: `src/pages/api/trips/auth.ts:11`
- **Issue**: The `attempts` Map is module-level state. On Vercel's serverless runtime each cold-start initialises a fresh Map, so the 5-attempt/60-second window resets whenever a new function instance spins up. An attacker on a 4-digit PIN space (10,000 combinations) can trivially exhaust the space by cycling requests fast enough to keep hitting fresh instances, or by waiting for natural instance recycling. The project already has Upstash Redis wired in via `src/lib/redis.ts`; persisting attempt counters there would provide durable rate limiting.
- **Fix**: Move rate-limit state to Redis using a key like `ratelimit:auth:<ip>` with a Redis TTL of 60 seconds and `INCR`/`EXPIRE` atomics. Fall back gracefully if Redis is unavailable (allow the request, log a warning) rather than hard-failing.

### Token payload is a raw timestamp with no expiry validation
- **File**: `src/middleware.ts:9-18` and `src/pages/api/trips/auth.ts:55-57`
- **Issue**: The HMAC token is `${timestamp}.${sig}` where the payload is `Date.now().toString()`. The middleware only verifies the signature; it never checks that the timestamp is within any window. The cookie `maxAge` is 30 days, but a stolen cookie is valid forever (the HMAC will always verify). There is no mechanism to invalidate a compromised token short of rotating `TRIP_SECRET`.
- **Fix**: Add an expiry claim to the payload (e.g., `${issuedAt}:${expiresAt}`) and verify in `verifyToken` that `Date.now() < expiresAt`. This bounds the blast radius of a stolen cookie and allows fine-grained session lifetimes without secret rotation.

### Default fallback secrets are hardcoded and will silently be used in production if env vars are unset
- **File**: `src/middleware.ts:7` and `src/pages/api/trips/auth.ts:6-7`
- **Issue**: Both `TRIP_SECRET` and `TRIP_PIN` fall back to `"dev-secret-change-me"` and `"0000"` respectively if the environment variables are not set. If a Vercel deployment is ever created without configuring these vars (e.g., a preview deployment, a fork, or an accidental env var deletion), the PIN is trivially guessable and all tokens signed with the fallback secret are forgeable by anyone who reads this source code.
- **Fix**: Replace the fallback with an explicit error thrown at startup: `if (!import.meta.env.TRIP_SECRET) throw new Error("TRIP_SECRET env var is required")`. Astro SSR routes run at request time, so an early-exit `Response` with a 500 and a log message is appropriate. At minimum, log a loud warning so Vercel's function logs make the misconfiguration obvious.

## Medium

### `/trips/login` open-redirect via unvalidated `next` query parameter
- **File**: `src/pages/trips/login.astro:41`
- **Issue**: The client-side login script reads `params.get("next") || "/trips/nyc-2026"` and passes it directly to `location.href` after a successful PIN auth. While the cookie is set server-side (so auth itself is not affected), the redirect destination is attacker-controlled. A phishing link like `/trips/login?next=https://evil.com` will redirect a successfully authenticated user to an external site. The `next` parameter is also written into the redirect URL by the middleware without any validation.
- **Fix**: In the login page script, validate that `next` starts with `/` and does not start with `//` before using it: `const safePath = (next && next.startsWith('/') && !next.startsWith('//')) ? next : '/trips/nyc-2026';`. Apply the same check in the middleware before appending the `next` param.

### `/api/trips/votes` returns a 200 OK when Redis is not configured, masking the error
- **File**: `src/pages/api/trips/votes.ts:12-15`
- **Issue**: When `getRedis()` returns `null` (no env vars), the endpoint returns `{ ok: false, error: "Redis not configured", votes: {} }` with HTTP status 200. The client in `nyc-2026.astro` checks `data.ok` and will silently show empty votes rather than surfacing the error. This means a misconfigured deployment looks like a working deployment with no votes cast, which could be confusing during onboarding or debugging.
- **Fix**: Return a 503 status code (as the vote POST endpoint already does) to make the misconfiguration visible in monitoring. Update the client-side `loadVotes()` to handle non-OK HTTP statuses explicitly.

### `VOTERS` list is duplicated between `src/lib/redis.ts` and `src/pages/trips/nyc-2026.astro`
- **File**: `src/lib/redis.ts:31` and `src/pages/trips/nyc-2026.astro:614`
- **Issue**: The authoritative voter list is defined in `redis.ts` as `export const VOTERS = ["brady", "stacy", "blake", "karsyn", "emrie"] as const;`, but `nyc-2026.astro` redeclares `const VOTERS = ["brady", "stacy", "blake", "karsyn", "emrie"] as const;` locally. If a voter is added or removed, one of these will be updated and the other forgotten, causing a silent divergence where the UI renders a voter the API rejects (or vice versa).
- **Fix**: Remove the local declaration in `nyc-2026.astro` and import `VOTERS` from `../../lib/redis`.

### `any` type casts suppress TypeScript checking in template loops
- **File**: `src/pages/trips/nyc-2026.astro:1318` and `src/pages/trips/nyc-2026.astro:1328`
- **Issue**: The day event and action items are typed as `any` in the template (`e: any`, `a: any`). Since the project uses `tsconfig.json` with `astro/tsconfigs/strict`, this silences the type system for all property accesses on these objects. Typos in property names (e.g., `e.voteable` vs `e.votable`) would not be caught at build time.
- **Fix**: Define an `Event` and `Action` interface in the frontmatter (or a shared types file) and apply them to the `days` array. The data structures are already well-defined in the frontmatter — lifting the shapes to explicit types is low-effort and high-value.
