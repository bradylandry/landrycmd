## High

### YAML frontmatter injection via single-quote bypass in `buildFrontmatter`
- **File**: `src/pages/api/publish-note.ts:18-33`
- **Issue**: `buildFrontmatter` wraps string values that contain a double-quote in single quotes (`'${v}'`). If `v` also contains a single quote (e.g. a title like `Brady's note`), the resulting YAML is `title: 'Brady's note'` — syntactically broken YAML. Worse, a crafted value like `foo' \ndraft: false\ntags: [injected]` would split the YAML document, potentially overwriting frontmatter keys set later in the loop. Because `title` and `content` both come from the request body (authenticated only by a static API key), any caller with the key can inject arbitrary frontmatter fields.
- **Fix**: Use a dedicated YAML-escaping approach. The simplest safe option is to always double-quote values and escape any embedded double-quotes (`v.replace(/\\/g, '\\\\').replace(/"/g, '\\"')`). Alternatively, switch to a small YAML serialisation library (`js-yaml`) to avoid hand-rolling the serialiser entirely.

### Missing TypeScript env-var declarations for publish-note secrets
- **File**: `src/env.d.ts:1-11` and `src/pages/api/publish-note.ts:5-7`
- **Issue**: `GITHUB_TOKEN`, `GITHUB_REPO`, and `PUBLISH_API_KEY` are read via `import.meta.env.*` but not declared in the `ImportMetaEnv` interface. TypeScript infers them as `any`, so a typo in an env-var name (e.g. `GITHUB_TOKENS`) silently returns `undefined` at build time, causing the 500 guard at line 45 to fire only in production. The same applies to server-side `process.env.*` fallbacks in `redis.ts` — those env vars are also undeclared.
- **Fix**: Add all server env vars to `src/env.d.ts`:
  ```ts
  readonly GITHUB_TOKEN: string;
  readonly GITHUB_REPO: string;
  readonly PUBLISH_API_KEY: string;
  ```
  This surfaces misconfiguration as a TS compile error rather than a production 500.

## Medium

### `publish-note.ts` does not sanitise the slug used as a file path
- **File**: `src/pages/api/publish-note.ts:70-72`
- **Issue**: When a caller supplies `slug` in the request body, it is used directly in `filePath = \`src/content/notes/${slug}.md\`` without validation. A slug like `../../src/pages/api/evil` would write a file outside the `notes/` directory via the GitHub Contents API. The auto-generated `slugify()` path is safe, but the `providedSlug` branch bypasses it entirely.
- **Fix**: Validate that `providedSlug` (when provided) matches the same `[a-z0-9-]+` pattern used by `slugify`, or apply `slugify` to it regardless.

### Rate-limit window race: counter incremented before expiry is set
- **File**: `src/pages/api/trips/auth.ts:24-26`
- **Issue**: The rate-limiter does `incr(key)` then — only if `count === 1` — does `expire(key, WINDOW_SEC)`. If two concurrent requests both see `count === 1` (possible when the key doesn't yet exist and two requests arrive simultaneously), one will set the expiry and one will silently skip it, leaving a key that never expires. The window effectively becomes infinite instead of 60 seconds. In practice this is a low-probability event on Upstash, but it is a latent correctness issue.
- **Fix**: Use a single Lua script to atomically increment and conditionally set the expiry, or use `SET key 0 NX EX 60` to initialise the key with a TTL before incrementing.

### `starbase-2026.astro` silently bypasses auth middleware
- **File**: `src/pages/trips/starbase-2026.astro:3` and `src/middleware.ts:6`
- **Issue**: `starbase-2026.astro` uses `export const prerender = true`. Pre-rendered pages are served as static files by Vercel and never pass through the Astro SSR middleware. The middleware's `/trips/*` gate therefore does not run for this page. It is listed in the `PUBLIC_TRIPS` array in middleware, confirming that public access is intentional. However, the middleware's `PUBLIC_TRIPS` check only runs for SSR requests; the `prerender = true` setting means the middleware is never even invoked, making the whitelist entry dead code for that page. This inconsistency could mislead a future developer into believing the middleware controls access to the page.
- **Fix**: Either (a) add a comment in both files documenting that `prerender = true` is the mechanism that makes the page public (the `PUBLIC_TRIPS` entry is a belt-and-suspenders no-op), or (b) switch to `prerender = false` and rely solely on the `PUBLIC_TRIPS` whitelist for consistency with how the nyc-2026 page (also under `/trips/`) handles auth bypass.

## Low

### Open-redirect protection on `?next=` is correct but undocumented
- **File**: `src/pages/trips/login.astro:41`
- **Issue**: The code `rawNext.startsWith("/") && !rawNext.startsWith("//")` correctly blocks protocol-relative redirects (`//evil.com`). However, it still allows any same-origin path, including unrelated pages on the site (e.g. `?next=/privacy`). This is low-risk but the intent is only to redirect within `/trips/`. A tighter guard (e.g. requiring `rawNext.startsWith("/trips/")`) would reduce the blast radius if a future XSS or CRLF issue were found elsewhere on the site.
- **Fix**: Change the check to `rawNext.startsWith("/trips/") && !rawNext.startsWith("//")` and update the fallback default to `/trips/nyc-2026`.

### External links on homepage missing `noreferrer`
- **File**: `src/pages/index.astro:75-84`
- **Issue**: External `<a>` tags use `rel="noopener"` but not `rel="noopener noreferrer"`. The missing `noreferrer` means the `Referer` header is sent to third-party sites (GitHub, LinkedIn, live product URLs), potentially leaking the referring path.
- **Fix**: Change `rel="noopener"` to `rel="noopener noreferrer"` on all external links in `index.astro`.

### `redis.ts` singleton is module-level but may be re-initialised across warm starts
- **File**: `src/lib/redis.ts:20-28`
- **Issue**: `_redis` is a module-level singleton. In Vercel's serverless model each function invocation within a warm container reuses the module, so this works correctly. However, the comment at the top of the file describes a nuanced env-var preference between `UPSTASH_*` and `KV_*`, but if both sets of vars are present and the `UPSTASH_*` vars point to a different project than `KV_*`, the silently-preferred URL from `UPSTASH_*` is used with no runtime warning. A developer rotating credentials who sets only the `KV_*` vars would silently hit the old instance.
- **Fix**: Add a `console.warn` (or even `console.error`) when both `UPSTASH_REDIS_REST_URL` and `KV_REST_API_URL` are set simultaneously, so the preference is visible in Vercel function logs during configuration changes.

### `publish-note.ts` reveals GitHub error details to the caller
- **File**: `src/pages/api/publish-note.ts:117`
- **Issue**: When the GitHub PUT fails, the raw GitHub API error body is forwarded to the caller in the `detail` field. This can expose internal information (branch names, repo structure hints, token scope errors). Because the endpoint is protected by `PUBLISH_API_KEY`, the exposure is only to authorised callers, reducing the risk significantly.
- **Fix**: Log the full error server-side and return only a generic message (`"GitHub commit failed — check server logs"`) to the caller.
