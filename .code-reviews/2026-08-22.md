## Medium

### `buildFrontmatter` produces invalid YAML for strings containing both quote types

- **File**: `src/pages/api/publish-note.ts:23-27`
- **Issue**: The function wraps values with `"` by default, or `'` when the value contains `"`. It doesn't handle the case where a value contains both `'` and `"` (e.g. `O'Brien says "hi"`). Wrapping in single quotes while the value contains an unescaped single quote produces syntactically invalid YAML, which would be committed to GitHub as a broken content file.
- **Fix**: Either (a) use a real YAML serialization library (`js-yaml`'s `dump()`), or (b) always double-quote all string values and escape any internal `"` with `\"`, which is safe and unambiguous:
  ```ts
  lines.push(`${k}: "${String(v).replace(/\\/g, '\\\\').replace(/"/g, '\\"')}"`);
  ```

### Non-constant-time HMAC comparison in `verifyToken`

- **File**: `src/middleware.ts:25`
- **Issue**: `expected !== sig` is a JavaScript string equality check, not a constant-time comparison. A sufficiently persistent attacker with many requests could extract the HMAC value byte-by-byte through timing. Rate limiting significantly reduces practical exploitability, but this contradicts the security contract of HMAC verification.
- **Fix**: Convert both hex/base64url strings to `Uint8Array` and compare with `crypto.subtle.timingSafeEqual` (available in the Web Crypto API):
  ```ts
  const expectedBytes = new TextEncoder().encode(expected);
  const sigBytes = new TextEncoder().encode(sig);
  if (expectedBytes.length !== sigBytes.length) return false;
  if (!crypto.subtle.timingSafeEqual(expectedBytes, sigBytes)) return false;
  ```

### `PUBLISH_API_KEY`, `GITHUB_TOKEN`, `GITHUB_REPO` missing from `env.d.ts`

- **File**: `src/env.d.ts:1` / `src/pages/api/publish-note.ts:5-7`
- **Issue**: `publish-note.ts` reads `PUBLISH_API_KEY`, `GITHUB_TOKEN`, and `GITHUB_REPO` from `import.meta.env`, but none of these are declared in the `ImportMetaEnv` interface. TypeScript treats undeclared env vars as `any`, so typos in the names won't produce a compile error.
- **Fix**: Add to `env.d.ts`:
  ```ts
  readonly GITHUB_TOKEN: string;
  readonly GITHUB_REPO: string;
  readonly PUBLISH_API_KEY: string;
  ```

### In-process rate-limit fallback doesn't coordinate across serverless instances

- **File**: `src/pages/api/trips/auth.ts:19-28`
- **Issue**: The `fallbackCounts` Map is in-process memory. On Vercel serverless, multiple concurrent worker instances each maintain independent counters, so the effective rate limit when Redis is down is `MAX_ATTEMPTS × instance_count`, not 5 attempts. The code's comments acknowledge this tradeoff (failing closed is the right call over failing open), but it's worth tracking if the PIN auth ever needs stronger guarantees.
- **Fix**: No immediate code change required — the current behavior is preferable to failing open. Consider logging instance ID alongside the fallback log line to make multi-instance effects observable.
