## High

### Path traversal via caller-supplied slug

- **File**: `src/pages/api/publish-note.ts:72`
- **Issue**: `providedSlug` is accepted from the request body and used directly as a file path component (`src/content/notes/${slug}.md`) in the GitHub Contents API call. No validation is applied. A caller with a valid `PUBLISH_API_KEY` can supply `slug: "../../../.github/workflows/evil"` to write arbitrary files anywhere in the repo — overwriting CI workflows, `package.json`, `astro.config.mjs`, or any other file.
- **Fix**: Validate the caller-supplied slug before use. Reject slugs that don't match a safe pattern and check the resolved path stays within `src/content/notes/`:
  ```ts
  if (providedSlug && !/^[a-z0-9][a-z0-9-]*[a-z0-9]$/.test(providedSlug)) {
    return new Response(JSON.stringify({ error: "Invalid slug" }), { status: 400, ... });
  }
  ```

### `buildFrontmatter` produces broken YAML for strings with newlines or mixed quotes

- **File**: `src/pages/api/publish-note.ts:18-37`
- **Issue**: The frontmatter builder only handles strings containing `"` by switching to single-quote wrapping (`'${v}'`). If `v` contains a newline character, neither branch produces valid YAML — the newline is emitted raw inside a quoted scalar, breaking Astro's content collection parser and failing the Vercel build. Similarly, a string containing both `"` and `'` (e.g., `it's "great"`) is silently mishandled.
- **Fix**: Use a proper YAML scalar escape for all strings. The simplest safe approach is to replace all newlines with a space and escape any remaining `"` characters, or strip control characters entirely before building the frontmatter:
  ```ts
  function yamlStr(v: string): string {
    const safe = v.replace(/[\x00-\x1f]/g, " ").replace(/"/g, '\\"');
    return `"${safe}"`;
  }
  ```

## Medium

### SHA lookup swallows all exceptions, not just 404

- **File**: `src/pages/api/publish-note.ts:88-96`
- **Issue**: The `catch {}` block that retrieves the existing file's SHA catches every error and treats it as "file doesn't exist." A transient network failure or timeout causes the PUT request to proceed without a SHA. GitHub returns 422 (`sha` required for updates) in this case, and the generic `"GitHub commit failed"` response surfaces to the caller with no indication of the real cause. A retry by the caller can then create a duplicate if the first request actually succeeded.
- **Fix**: Distinguish 404 (no file) from other errors:
  ```ts
  const existing = await fetch(ghBase, { headers: ghHeaders });
  if (existing.ok) {
    const data = await existing.json() as { sha: string };
    sha = data.sha;
  } else if (existing.status !== 404) {
    return new Response(JSON.stringify({ error: "Failed to check existing file" }), { status: 502, ... });
  }
  ```

### Missing `ImportMetaEnv` declarations for publish-note env vars

- **File**: `src/env.d.ts:1-9`
- **Issue**: `GITHUB_TOKEN`, `GITHUB_REPO`, and `PUBLISH_API_KEY` are accessed via `import.meta.env` in `publish-note.ts` but are not declared in the `ImportMetaEnv` interface. TypeScript will type them as `any`, so typos in variable names (e.g., `GITHUB_TOKENS`) won't be caught at compile time.
- **Fix**: Add the three declarations to `ImportMetaEnv`:
  ```ts
  readonly GITHUB_TOKEN: string;
  readonly GITHUB_REPO: string;
  readonly PUBLISH_API_KEY: string;
  ```

## Low

### In-process rate-limit fallback map grows without bound

- **File**: `src/pages/api/trips/auth.ts:17-32`
- **Issue**: `fallbackCounts` is a module-level `Map` with no eviction. Entries expire logically (checked via `expiresAt`) but are never deleted from the map. On serverless platforms (Vercel) function lifetimes are short enough that this is practically harmless, but if the function is kept warm for an extended period under Redis outage, the map accumulates one entry per unique IP indefinitely.
- **Fix**: Delete expired entries on access: add `fallbackCounts.delete(ip)` alongside the `set` call when `!entry || now > entry.expiresAt`.
