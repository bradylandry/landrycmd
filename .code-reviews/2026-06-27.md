## High

### YAML injection in `buildFrontmatter` allows frontmatter smuggling
- **File**: `src/pages/api/publish-note.ts:18–33`
- **Issue**: The `buildFrontmatter` helper quotes string values naively. A title or description containing a single-quote (`'`) will break out of the `'…'` branch (line 25) and inject raw YAML. Example: a title of `foo' \ndraft: false\ntags: [injected]` produces malformed/injected frontmatter. The `'"'`-contains check on line 24 only switches quoting style; it does not escape the value itself. An attacker with access to the API key can craft a note whose frontmatter overrides `draft`, `date`, or any other field, or break the YAML parser entirely causing a build failure.
- **Fix**: Use a proper YAML serialization library (e.g. `js-yaml`'s `dump`) instead of string concatenation, or at minimum escape embedded quotes: for the `'`-quoted branch, replace every `'` in the value with `''` (YAML single-quote escape). Also validate/strip newlines from all string fields before writing frontmatter.

### Private trip page (`nyc-2026.astro`) is publicly accessible — no auth gate
- **File**: `src/pages/trips/nyc-2026.astro:4` and `src/middleware.ts:6`
- **Issue**: The middleware `PUBLIC_TRIPS` array only contains `"/trips/starbase-2026"`. The `/trips/nyc-2026` route is SSR (`prerender = false`) and is correctly _not_ listed in `PUBLIC_TRIPS`, so middleware should gate it. However, the page still passes the middleware `!SECRET` check at line 58 — if `TRIP_SECRET` is not set in a preview/staging deployment the request falls through with a 500, and Vercel preview deployments that don't inherit production secrets will return 500 rather than 401. More importantly: the page contains highly specific PII — full names, flight confirmation codes (`DL 5308`, `DL 490`, `DL 2227`), seat assignments, hotel confirmation codes (`TF88GC3` for Wicked, LUXY booking codes `DD38-5NSM` / `EEIW-BR3G`), phone numbers, and full addresses. If `TRIP_SECRET` is ever missing from a deployment, this data is exposed. The auth guard being purely middleware-based (not enforced at the page level) is a single point of failure.
- **Fix**: (1) Immediately move all confirmation codes and booking references out of the page source and into a data file loaded server-side from an environment variable or Redis, so they are never in the static build output or git history. (2) Add a server-side auth check inside the page's frontmatter block as a defense-in-depth fallback, similar to what `vote.ts` does with `verifyToken`.

## Medium

### `GITHUB_TOKEN` and `PUBLISH_API_KEY` missing from `ImportMetaEnv`
- **File**: `src/env.d.ts:1–11`
- **Issue**: `GITHUB_TOKEN`, `GITHUB_REPO`, and `PUBLISH_API_KEY` are accessed via `import.meta.env` in `publish-note.ts` but are not declared in the `ImportMetaEnv` interface. TypeScript's strict mode will type these as `any` (the Vite default for unknown env vars). This removes compile-time checking that the vars exist, and masks typos.
- **Fix**: Add `readonly GITHUB_TOKEN: string; readonly GITHUB_REPO: string; readonly PUBLISH_API_KEY: string;` to `ImportMetaEnv` in `src/env.d.ts`.

### Rate-limit bypass via IPv6 / X-Forwarded-For header spoofing
- **File**: `src/pages/api/trips/auth.ts:15–27`
- **Issue**: The rate limiter keys on `clientAddress`, which on Vercel's serverless adapter is derived from the inbound request's IP. If the Vercel project is placed behind a proxy or CDN that forwards `X-Forwarded-For`, the effective `clientAddress` may be attacker-controlled. Additionally, IPv6 addresses give a large address space that makes IP-based rate limiting trivially bypassable even without header manipulation. The current `MAX_ATTEMPTS = 5` per minute per IP is low enough to prevent casual brute-force, but 4-digit PINs (10,000 combinations) are fully enumerable if the rate limit can be bypassed.
- **Fix**: For a 4-digit PIN, consider adding a global attempt counter per-PIN (not per-IP) with a short lockout after N failures regardless of source IP, or move to a longer/alphanumeric shared secret. Document the Vercel trusted-proxy header configuration that locks down which IPs are allowed to set `X-Forwarded-For`.

### Booking confirmation codes and PII in git history
- **File**: `src/pages/trips/nyc-2026.astro:128–132, 339, 665–668`
- **Issue**: The file hard-codes LUXY booking confirmation codes (`DD38-5NSM`, `EEIW-BR3G`), Wicked box office code (`TF88GC3`), order number (`206502940-7757062`), flight numbers and seat assignments for 5 people, full hotel address, and personal names. These are checked into git and will persist in history even if removed later. While the page is auth-gated at runtime, this data lives permanently in the repository.
- **Fix**: Move booking references to a separate data file or environment variable that is `.gitignore`d. At minimum, document that this git repo should remain private. The current `.gitignore` does not indicate the repo is private.

## Low

### `sign` function is exported but intended as private
- **File**: `src/middleware.ts:76`
- **Issue**: `export { sign, COOKIE_NAME }` exports the `sign` function from the middleware barrel. `sign` is an internal HMAC helper; exporting it from the module invites accidental misuse (e.g., calling it directly without going through `verifyToken`'s timing-safe comparison). Only `verifyToken` and `COOKIE_NAME` need to be public — `sign` is only needed by `auth.ts` which already uses the correct call path.
- **Fix**: Remove `sign` from the export and have `auth.ts` call `verifyToken`'s internal implementation, or create a separate shared `crypto.ts` with explicit documentation that `sign` is internal.

### `buildFrontmatter` silently drops `undefined`/`null` values as literal strings
- **File**: `src/pages/api/publish-note.ts:18–33`
- **Issue**: The `else` branch (`lines.push(\`${k}: ${v}\`);`) will serialize `null` as the string `"null"` and `undefined` as `"undefined"` in the YAML output, which YAML will parse back as strings rather than null/undefined. This is a latent correctness bug for any caller that passes nullable values.
- **Fix**: Add an explicit check to skip `null`/`undefined` values, or convert them to YAML `~` / `null`.
