## High

### Redis unavailability returns misleading 429 on auth
- **File**: `src/pages/api/trips/auth.ts:16-24`
- **Issue**: `checkRateLimit` returns `false` when Redis is unreachable, and the caller treats any `false` return as rate-limit exhaustion, responding with HTTP 429 and the message `"Too many attempts. Wait a minute."` A Redis outage locks every user out with an error that implies they did something wrong, and the console error is the only trace.
- **Fix**: Distinguish the two failure modes. When Redis is `null`, either fail open (return `true` and allow the attempt through) and emit an alert, or return a dedicated sentinel and respond with 503. At minimum, change the error body to reflect the actual problem:
  ```ts
  if (!redis) {
    console.error("Rate limiter: Redis unavailable for", ip);
    // fail open — log but don't block when limiter is down
    return true;
  }
  ```

### `clientAddress` fallback collapses all users into a shared rate-limit bucket
- **File**: `src/pages/api/trips/auth.ts:27`
- **Issue**: `const ip = clientAddress || "unknown"` — if the Vercel adapter fails to populate `clientAddress` (or in local dev), every request is keyed to `ratelimit:auth:unknown`. Five total auth attempts from anywhere lock out all users for 60 seconds. This is simultaneously a denial-of-service vector (attacker sends 5 requests → everyone locked out) and a silent bypass (attacker can rotate IPs while all share the same key).
- **Fix**: Throw or return early if `clientAddress` is missing, rather than substituting a shared sentinel:
  ```ts
  if (!clientAddress) {
    console.error("clientAddress not provided by adapter — cannot rate-limit");
    return new Response(JSON.stringify({ ok: false, error: "Server error" }), { status: 500, ... });
  }
  const ip = clientAddress;
  ```

## Medium

### Any authenticated user can vote on behalf of any family member
- **File**: `src/pages/api/trips/vote.ts:37-54`
- **Issue**: The `voter` field is taken directly from the request body. Any holder of a valid auth cookie can submit votes attributed to `brady`, `stacy`, `blake`, `karsyn`, or `emrie` — no binding exists between the token and an identity. For a private family app this is probably acceptable by design, but it means a single shared PIN allows impersonation.
- **Fix**: If individual voter identities matter, encode the voter name in the auth token at issue time, verify it server-side, and reject requests where the body `voter` doesn't match the token claim. If intentional, document it explicitly in the code.

### `/_trip-style.css` link in login page is a dead asset reference
- **File**: `src/pages/trips/login.astro:7`
- **Issue**: `<link slot="head" rel="stylesheet" href="/_trip-style.css" />` references a file that does not exist under `public/` (only `favicon.svg` and `robots.txt` are there). Every login page load fires a 404 for this asset. The styles still render correctly because `<style>@import "../../styles/trip.css";</style>` (line 130) is bundled at build time — but the dead HTTP request adds latency and noise to browser devtools and Vercel logs.
- **Fix**: Remove the `<link>` tag entirely since the `<style>` block already covers the styles.

### `verifyToken` uses the module-level `SECRET` which can be empty string
- **File**: `src/middleware.ts:8` and `src/pages/api/trips/vote.ts:12`, `src/pages/api/trips/votes.ts:11`
- **Issue**: `const SECRET = import.meta.env.TRIP_SECRET || "";`. The middleware guards against an empty `SECRET` with a 500 response, but `verifyToken` (imported by vote.ts and votes.ts) uses the same module-level `SECRET` directly with no independent guard. If `TRIP_SECRET` is unset, `sign(payload, "")` generates valid-looking tokens that can be constructed externally — though the auth route's own 500 guard means no legitimate tokens can be issued to exploit this.
- **Fix**: Guard in `verifyToken` itself so callers don't rely on the middleware check:
  ```ts
  export async function verifyToken(token: string): Promise<boolean> {
    if (!SECRET) return false;
    ...
  }
  ```

## Low

### Weather data is hardcoded placeholder
- **File**: `src/pages/trips/nyc-2026.astro:1070-1079`
- **Issue**: Comment reads `// Average June NYC weather (placeholder — swap for live API later)`. Temperature values are static and do not update. If the trip is viewed close to departure, users may be misled by stale forecast data.
- **Fix**: Wire to a weather API (e.g. Open-Meteo) server-side at build or SSR time, or clearly label the section "Historical averages" if real-time data is out of scope.

### `nyc-2026.astro` is 1,603 lines — entire trip defined inline
- **File**: `src/pages/trips/nyc-2026.astro:1-1603`
- **Issue**: All flight data, day events, alternates, vote options, SVG glyphs, and UI are co-located in a single file. Updating a restaurant or flight detail requires editing a deeply nested data structure inside an Astro page. Any data errors (wrong confirmation code, outdated seat assignment) require a code deploy.
- **Fix**: Extract the trip data (`days`, `flights`, `reservations`, etc.) to a typed `src/data/nyc-2026.ts` module. The Astro page becomes a pure rendering layer.

### `<Layout>` emits `og:url` using canonical path even for noindex pages
- **File**: `src/layouts/Layout.astro:28-29`
- **Issue**: The `<meta property="og:url">` tag always uses the canonical URL, including on `/trips/*` pages that have `noindex,nofollow,noarchive`. The canonical `<link>` is suppressed for private pages (line 23-24), but OG metadata still exposes the path. This is low risk since crawlers won't index the page, but OG scrapers (e.g. link unfurlers) could reveal that the path exists.
- **Fix**: Suppress the OG block for private pages alongside the canonical suppression.
